    System monitoring

    Core Module

    A model that passed every test on your laptop can still fail in production: the container runs out of memory, a client starts sending broken requests, answers get slow, or the images people send stop looking like the ones the model was trained on. Monitoring is how you find out before your users tell you. We look at a deployed model at four monitoring layers:

    Layer The question it answers Example signal
    System Is the machine and the process healthy? Is the target up, memory, CPU
    Service Are requests answered, how fast, and how often do they fail? Request rate, p95 latency, error rate
    Data Does the input still look like what the model was trained on? Drift of image features against the reference data
    Model Are the predictions still good? Share of each predicted class, mean confidence, accuracy once labels arrive

    This session has three modules. In this one, System monitoring, you cover the system and service layers: you instrument an image classifier API with Prometheus metrics, look at it in Grafana, move the whole thing to the cloud and make an alert reach your phone. In Data drifting you store a production window and fill in the data and model layers. In Closing the loop, newly labelled data flows back into training and a better model gets deployed.

    traffic.py ──▶ /predict  (FastAPI API, on Cloud Run) ◀── scrapes /metrics ── Prometheus ◀── queries ── Grafana ──▶ Discord
                                                                             └────── always-on VM ──────┘    (alert)

    The module takes about 2.5 hours. Steps that take a while say so, so you can plan around them.

    Learning objectives

    The learning objectives of this module are:

    • Know the four monitoring layers and which signals belong to each
    • Be able to instrument a Python API with Prometheus counters and histograms, and read the result with PromQL
    • Be able to run Prometheus and Grafana with docker compose, with the Grafana data source and dashboard provisioned from files
    • Understand why scraping a serverless service only works while it runs one instance, and what production systems do instead
    • Be able to run a monitoring stack on a VM you sized yourself, with no open ports, and send an alert to a channel

    Everything in this module happens in one self-contained folder: s8_monitoring/exercise_files/monitoring_stack. It holds a small FastAPI app, much like the one you built in M22 on APIs, that classifies images of hands showing rock, paper or scissors (RPS).       Solution

    Instrumenting the API with Prometheus

    Prometheus is the standard open-source system for metrics. It works by pulling: your application keeps its metrics in memory and exposes their current values on an HTTP endpoint, usually /metrics, in a simple text format. Every few seconds the Prometheus server fetches ("scrapes") that endpoint and stores the values as time series. The application never sends anything anywhere; it only counts.

    ❔ Exercises

    1. Read about the metric types. What is the difference between a counter, a gauge, a histogram and a summary? Which type would you use for the number of answered requests, for the time each request takes, and for the current number of images in a queue?

      Solution
      • A counter only goes up (or resets to zero when the process restarts). Use it for things that happen: the number of answered requests, the number of errors. You almost never look at a counter's raw value, but at how fast it grows: rate(...).
      • A gauge goes up and down. Use it for things that are: memory in use, the number of images in a queue, the temperature.
      • A histogram counts observations in buckets (for example "answered in under 10 ms") plus their sum and count. Use it for durations and sizes. Prometheus can compute quantiles such as p95 from the buckets, and the buckets of many instances can be added up.
      • A summary computes quantiles inside the application. They cannot be added up across instances, so histograms are usually the better choice.

      The number of requests is a counter, the time per request a histogram, the queue length a gauge.

    2. Open api.py and fill in the three TODOs with the prometheus_client library:

      1. a counter predict_requests_total of answered requests, labelled with the predicted class;
      2. a histogram predict_latency_seconds of how long each answer takes;
      3. a counter predict_errors_total of rejected requests, labelled with the reason.

      Prometheus measures time in seconds, so the histogram is in seconds too. Our answers take milliseconds, so the default buckets (5 ms up to 10 s) would put almost everything in the first few. Use the millisecond-scale buckets given in the TODO.

      """The classifier as an HTTP API, instrumented with Prometheus metrics.

    uv run uvicorn api_solution:app --port 8000      # directly, without Docker
    docker compose up -d --build                     # together with Prometheus and Grafana (see compose.yaml)

POST an image to /predict and get the class, the confidence and the model version back. Prometheus scrapes /metrics.

Environment: MODEL_CHECKPOINT, the checkpoint to serve (default: models/model.pt).
"""

import os
import time
from contextlib import asynccontextmanager

import torch
from dataset import CLASSES, BadImageError, decode, preprocess
from fastapi import FastAPI, File, HTTPException, UploadFile
from fastapi.responses import Response
from model import load_checkpoint
from prometheus_client import CONTENT_TYPE_LATEST, REGISTRY, Counter, Histogram, generate_latest

# --- service layer metrics ---------------------------------------------------------------------------------------
REQUESTS_TOTAL = Counter(
    "predict_requests_total",
    "Answered /predict requests, by predicted class",
    ["predicted_class"],
)
LATENCY = Histogram(
    "predict_latency_seconds",
    "Time to answer a /predict request",
    buckets=(0.001, 0.0025, 0.005, 0.01, 0.025, 0.05, 0.1, 0.25, 0.5, 1.0),
)
ERRORS = Counter("predict_errors_total", "Rejected /predict requests, by reason", ["reason"])

state = {}


@asynccontextmanager
async def lifespan(app: FastAPI):
    """Load the model once, when the service starts."""
    torch.set_num_threads(1)
    state["model"], state["version"] = load_checkpoint(os.environ.get("MODEL_CHECKPOINT", "models/model.pt"))
    print(f"serving model version {state['version']}", flush=True)
    yield
    state.clear()


app = FastAPI(title="Image classifier", lifespan=lifespan)


@app.get("/health")
def health() -> dict:
    """Liveness check that also says which model version is served."""
    return {"status": "ok", "model_version": state["version"]}


@app.post("/predict")
def predict(file: UploadFile = File(...)) -> dict:
    """Classify one image."""
    start = time.perf_counter()
    try:
        img = decode(file.file.read())
    except BadImageError as err:
        ERRORS.labels(reason=err.reason).inc()
        raise HTTPException(status_code=400, detail=str(err)) from None

    with torch.no_grad():
        probs = state["model"](preprocess(img)[None]).softmax(1)[0]
    k = int(probs.argmax())

    REQUESTS_TOTAL.labels(predicted_class=CLASSES[k]).inc()
    LATENCY.observe(time.perf_counter() - start)
    return {"class": CLASSES[k], "confidence": round(float(probs[k]), 4), "model_version": state["version"]}


@app.get("/metrics")
def metrics() -> Response:
    """Every metric in the default registry, in Prometheus' text format."""
    return Response(generate_latest(REGISTRY), media_type=CONTENT_TYPE_LATEST)

      Open http://localhost:8000/docs, choose POST /predict → Try it out, upload an image from data/rps-test-set/ and Execute. Then open http://localhost:8000/metrics. Which of your three metrics have a value already? Why does one of them show only its # HELP and # TYPE lines?

      Solution

      predict_requests_total has one sample, for the class that was predicted, and predict_latency_seconds has its buckets, _count and _sum. predict_errors_total shows only # HELP and # TYPE: it has a label, reason, and a labelled metric has one time series per label value. Nothing has been rejected yet, so no label value exists and there is no series to show. The series for reason="not_an_image" appears the first time that reason is counted. A metric without labels would show 0 right away.

      This matters later: until the first error, a query such as sum(rate(predict_errors_total[1m])) returns no data, not zero. Dashboards show an empty panel, and alerts have to be told what "no data" means.

    4. Why are there many more metrics on /metrics than the three you added? Which monitoring layer do they belong to?

      Solution

      prometheus_client registers some collectors in its default registry by itself: process_* (resident memory, CPU seconds, open file descriptors, start time) and python_* (garbage collector, interpreter version). They describe the process, not the requests, so they belong to the system layer. The three metrics you added are the service layer. (If you only want your own metrics, you can create your own CollectorRegistry and expose that instead.)

      """Replay a folder of images through the API, as production traffic: images only, no labels.

    uv run python traffic.py data/rps-test-set                       # the local API
    uv run python traffic.py data/rps-test-set --repeat 5 --delay 0.05
    uv run python traffic.py data/rps-test-set --url https://<your-service>.run.app

The images are sent in shuffled order, with a few malformed requests mixed in, as real clients send.
"""

import argparse
import io
import random
import time
from pathlib import Path

import requests
from dataset import image_files
from PIL import Image


def malformed(rng: random.Random) -> bytes:
    """A request a real client sends by mistake: not an image, a cut-off image or an empty file."""
    kind = rng.choice(["text", "truncated", "empty"])
    if kind == "text":
        return b"image not available, try again later\n"
    if kind == "empty":
        return b""
    buf = io.BytesIO()
    Image.new("RGB", (200, 200), (200, 180, 160)).save(buf, format="JPEG")
    return buf.getvalue()[: len(buf.getvalue()) // 2]


def main() -> None:
    """Send every image in the folder to /predict, ``--repeat`` times."""
    parser = argparse.ArgumentParser(description=__doc__, formatter_class=argparse.RawDescriptionHelpFormatter)
    parser.add_argument("folder", type=Path, help="a folder of images; subfolders are included")
    parser.add_argument("--url", default="http://localhost:8000")
    parser.add_argument("--repeat", type=int, default=1, help="replay the folder this many times")
    parser.add_argument("--delay", type=float, default=0.0, help="seconds to wait between requests")
    parser.add_argument("--malformed-every", type=int, default=50, help="one malformed request per N images")
    parser.add_argument("--seed", type=int, default=0)
    args = parser.parse_args()

    paths = image_files(args.folder)
    if not paths:
        msg = f"no images in {args.folder}"
        raise SystemExit(msg)
    rng = random.Random(args.seed)
    session = requests.Session()
    try:
        version = session.get(f"{args.url}/health", timeout=30).json()["model_version"]
    except requests.ConnectionError:
        msg = f"no API at {args.url}: is it running?"
        raise SystemExit(msg) from None
    print(f"sending {args.repeat} x {len(paths)} images to {args.url} (model version {version})")

    answered, rejected, sent = 0, 0, 0
    started = time.time()
    for _ in range(args.repeat):
        rng.shuffle(paths)
        for path in paths:
            sent += 1
            if sent % args.malformed_every == 0:
                r = session.post(f"{args.url}/predict", files={"file": ("image.jpg", malformed(rng))}, timeout=30)
                rejected += r.status_code != 200
            # A neutral file name: the API must not be able to read the class from it.
            files = {"file": ("image" + path.suffix, path.read_bytes())}
            r = session.post(f"{args.url}/predict", files=files, timeout=30)
            if r.status_code == 200:
                answered += 1
            else:
                rejected += 1
            if sent % 200 == 0:
                print(f"  {sent} images sent, {answered} answered, {rejected} rejected", flush=True)
            time.sleep(args.delay)
    print(f"done in {time.time() - started:.0f} s: {answered} answered, {rejected} rejected")


if __name__ == "__main__":
    main()

      Open Prometheus at http://localhost:9090, then Status → Target health. The api target should be UP. The Prometheus configuration scrapes api:8000, not localhost:8000. Why?

      Solution

      Each container has its own network namespace, so localhost inside the Prometheus container is the Prometheus container itself. Compose puts all services on one network where each is reachable by its service name, so the API is api:8000. The same goes for Grafana reaching Prometheus at http://prometheus:9090. The 127.0.0.1:8000:8000 port mapping is only for you, on the host.

    2. Generate some steady traffic (about a minute) and try these four starter queries in Prometheus, under Query, in the Graph tab:

      uv run python traffic.py data/rps-test-set --repeat 5 --delay 0.03

      sum(rate(predict_requests_total[1m]))
histogram_quantile(0.95, sum by (le) (rate(predict_latency_seconds_bucket[1m])))

      What does each query show, in which unit? What is the p95 latency? Is the service healthy?

      Solution
      1. The request rate: answered requests per second, averaged over the last minute. rate() turns an ever-growing counter into a per-second speed, and handles the counter resetting when the API restarts.
      2. The p95 latency in seconds: 95% of the requests in the last minute were answered faster than this. histogram_quantile estimates it from the buckets, so it is only as precise as the buckets around it. Expect a few milliseconds to a few tens of milliseconds on a laptop.
      3. The error rate: rejected requests per second. Divide it by the total to get the share of requests that fail, which is what you alert on later.
      4. The requests by predicted class, one line per class. This one sits on the border between the service and the model layer: it is counted per request, but a change in the mix of predictions is an early hint that the input has changed.

      The service is healthy if the target is up, the latency is low and stable, and the error share stays at the level the traffic script causes (about 2%).

    Moving the stack to the cloud

    In the cloud the API runs on Cloud Run, as in M23 on cloud deployment. Prometheus and Grafana can't run there: Cloud Run scales to zero and restarts containers whenever it likes, and a monitoring system has to be running exactly when everything else is not. So they run on an always-on Compute Engine VM, which you size yourself.

    This part costs money

    The VM and the Cloud Run service with a minimum of one instance are billed every hour they exist, whether you use them or not. The next modules reuse both, so keep them until the end of the day, but stop them as described in Stop what is billed when you are done.

    ❔ Exercises

    1. Build the API image for linux/amd64 (needed on Apple Silicon, harmless elsewhere) and push it to Artifact Registry. This takes 5 to 10 minutes, mostly for the upload.

      export PROJECT=$(gcloud config get-value project) REGION=europe-west1 ZONE=europe-west1-b
gcloud artifacts repositories create monitoring --repository-format=docker --location=$REGION
gcloud auth configure-docker $REGION-docker.pkg.dev
export IMAGE=$REGION-docker.pkg.dev/$PROJECT/monitoring/classifier-api:v1
docker build --platform linux/amd64 -f api.dockerfile -t $IMAGE .
docker push $IMAGE

    2. Deploy it to Cloud Run with exactly one instance and instance-based billing (about 2 minutes):

      gcloud run deploy classifier-api --image=$IMAGE --region=$REGION \
    --min-instances=1 --max-instances=1 --no-cpu-throttling \
    --memory=1Gi --allow-unauthenticated

      --no-cpu-throttling is how gcloud spells instance-based billing (formerly "CPU always allocated"). Replay some traffic against the URL gcloud printed, and look at its /metrics:

      export API_URL=$(gcloud run services describe classifier-api --region=$REGION --format='value(status.url)')
uv run python traffic.py data/rps-test-set --url $API_URL
curl -s $API_URL/metrics | grep predict_

      Why do we pin the service to exactly one instance, and why instance-based billing?

      Solution

      The metrics live in the memory of the instance that counted them. With exactly one instance, every scrape of the URL reaches the same counters, so the numbers Prometheus stores are right. --min-instances=1 keeps that instance from scaling to zero (which would reset every counter), --max-instances=1 keeps a second one from appearing. With request-based billing Cloud Run throttles the CPU outside of requests; with instance-based billing the instance keeps its CPU between requests, which the next module needs when the API writes the production window in the background. Since the instance runs all the time anyway, you pay for it all the time in both models.

    Why scraping a Cloud Run URL breaks once the service autoscales

    Prometheus scrapes one URL, but behind it Cloud Run load-balances over all running instances. With three instances, each scrape reaches a random one, and each instance has its own counters: one scrape sees 120 requests, the next 40, the next 300. rate() reads every drop as a counter reset and the graphs turn into noise. When an instance is shut down, its counts disappear with it. The setup in this module is therefore only correct while max-instances=1, which is fine for learning and wrong for a real service. Production setups do one of two things instead:

    • collect inside each instance: a collector runs as a sidecar container next to every instance, for example the Managed Service for Prometheus sidecar for Cloud Run, and labels the metrics with the instance they came from;
    • push instead of being pulled: each instance sends its metrics with OTLP (see OpenTelemetry below) to a collector or to Prometheus' OTLP receiver.

    /metrics is public

    --allow-unauthenticated makes every endpoint public, /metrics included. Anyone with the URL can read how much traffic you get and what your model predicts, and Cloud Run serves a container on a single port, so you can't hide /metrics on a second one. That is acceptable for these exercises. In a real service you would require authentication on the endpoint, or use the sidecar or push setups above, which don't expose metrics on the public URL at all.

    ❔ Exercises

    1. Before you create the VM, decide how big it has to be. Measure what Prometheus and Grafana use on your laptop while traffic runs:

      uv run python traffic.py data/rps-test-set --repeat 10 --delay 0.03 &
docker stats --no-stream monitoring-stack-prometheus-1 monitoring-stack-grafana-1
docker system df -v | grep monitoring-stack     # how much disk the volumes use so far
gcloud compute machine-types list --zones=$ZONE --filter="name~'^e2-'"

      Click around your Grafana dashboard while you measure: Grafana uses most when someone is looking. How much CPU and memory does the stack use? What else runs on the VM, and how much headroom do you add? Which machine type do you choose, and what does it cost per month? Write the numbers down; you will check them on the VM.

      Solution

      There is no single right answer, only a method:

      1. Take the peak, not the average, of the CPU and memory columns of docker stats for each container, and add them up.
      2. Add what runs besides the containers: the operating system and the Docker daemon need a few hundred MB.
      3. Add what is coming: the next module adds a Pushgateway and a scheduled drift job on the same VM, and the drift job loads images into memory. Prometheus also grows with the number of time series and how long it keeps them (15 days by default); docker system df -v tells you the disk side.
      4. Add headroom, for example 50%: a VM that swaps or kills Prometheus for lack of memory stops monitoring exactly when you need it.
      5. Pick the smallest machine type above that, and look up its price in the pricing calculator. Shared-core types (e2-micro, e2-small, e2-medium) are cheap and fine for bursty, light load, but check their memory against your sum.

      If you guessed wrong, you can change the machine type later: stop the VM, gcloud compute instances set-machine-type, start it again.

    2. Create the VM with the machine type you chose and install Docker on it. This takes about 5 minutes.

      gcloud compute instances create monitoring-vm --zone=$ZONE --machine-type=<your choice> \
    --image-family=ubuntu-2404-lts-amd64 --image-project=ubuntu-os-cloud --boot-disk-size=20GB
gcloud compute ssh monitoring-vm --zone=$ZONE --command \
    "sudo apt-get update && sudo apt-get install -y docker.io docker-compose-v2 && sudo usermod -aG docker \$USER"

      We create no firewall rules. The only way into the VM is SSH, through the default-allow-ssh rule of the default network, and Prometheus and Grafana listen on the VM's 127.0.0.1 only.

      The target is the host name only, without https:// and without a path: scheme: https makes Prometheus use HTTPS on port 443, and /metrics is the default path.

          static_configs:
      - targets: ["classifier-api-abc123xyz-ew.a.run.app"]

      echo $API_URL | sed 's#https://##' gives you the host name. If you changed the file after starting, restart Prometheus: PROMETHEUS_CONFIG=./prometheus.cloud.yml docker compose up -d --force-recreate prometheus.

    4. Reach Grafana through an SSH tunnel. Stop your local stack first (docker compose down on your laptop), because the tunnel uses the same ports:

      gcloud compute ssh monitoring-vm --zone=$ZONE -- -N -L 3000:localhost:3000 -L 9090:localhost:9090

      While this runs, http://localhost:3000 on your laptop is Grafana on the VM, and http://localhost:9090 is its Prometheus. Check that the api target is up and that your provisioned dashboard is there, then replay traffic against Cloud Run and watch it arrive. Who on the internet can reach Grafana now? What happens to the monitoring when you close the tunnel?

      Solution

      Only someone who can SSH into the VM, which gcloud compute ssh limits to members of your project with the right IAM role. Nothing listens on a public port: there is no firewall rule for 3000 or 9090, and the containers publish on 127.0.0.1 only, so even a firewall mistake would not expose them. That matters here, because this Grafana makes every visitor an admin. Closing the tunnel only closes your window into it: Prometheus keeps scraping and Grafana keeps evaluating alerts on the VM.

      For an even stricter setup, delete the default-allow-ssh rule and connect with --tunnel-through-iap: SSH then goes through Google's Identity-Aware Proxy and the VM needs no rule open to the internet at all.

    5. Check your sizing: on the VM, run docker stats --no-stream and free -m while you replay traffic and use the dashboard. Was your estimate right?

    Alerting

    A dashboard only helps when someone looks at it. An alert is a query that Grafana evaluates on a schedule, which sends a message when the result crosses a threshold for long enough. The hard part is not the mechanics, it is choosing what deserves to wake someone up. Too many alerts and people stop reading them (alert fatigue); too few and real problems go unnoticed.

    The rule of thumb is alert on symptoms, put drift on dashboards. Page a human for what users feel right now: the service fails requests, or answers slowly. Those are symptoms, they are clear-cut, and someone can act on them at once. Data drift and model-layer signals are different: a drift statistic crossing a threshold does not mean that users are affected, the thresholds are judgement calls, and the right response (look into it, collect labels, retrain) is days of work, not a 3 a.m. fix. They belong on the dashboard you look at during the day, which is where the next module puts them.

    ❔ Exercises

    1. Create a channel for alerts in Discord: on a server you own (create one if needed), Edit Channel → Integrations → Webhooks → New Webhook → Copy Webhook URL. Treat the URL as a secret: anyone who has it can post to your channel. Don't commit it.

    2. In Grafana, add a contact point: Alerting → Contact points → Create contact point, integration Discord, paste the webhook URL. Use Test to check that a message arrives. The contact point is stored in the grafana-data volume on the VM, not in your files.

    3. Create an alert rule on the share of failing requests (Alerting → Alert rules → New alert rule). Fire when more than 5% of requests fail for a minute, and send it to your Discord contact point. What do you set for "no data", and why?

      Solution

      • Query (data source Prometheus):

        sum(rate(predict_errors_total[1m]))
  / (sum(rate(predict_requests_total[1m])) + sum(rate(predict_errors_total[1m])))

      • Alert condition: the query is above 0.05 (in the advanced options: Reduce with Last, then Threshold is above 0.05).

      • Folder and evaluation group: any, evaluated every 1m, with a pending period of 1m.
      • Configure no data and error handling: set Alert state if no data to Normal. Until the first error the error counter has no series at all (the # HELP/# TYPE exercise), so the query returns no data, and without traffic the division has nothing to divide. Neither means the service is failing. (If the API itself is down, up{job="api"} == 0 is the signal for that, and would be a good second alert.)
      • Contact point: your Discord contact point. Add a summary, for example More than 5% of /predict requests fail.

      A p95 latency rule works the same way, with histogram_quantile(0.95, sum by (le) (rate(predict_latency_seconds_bucket[1m]))) and a threshold in seconds.

    4. Trigger it on purpose, with one malformed request for every second image:

      uv run python traffic.py data/rps-test-set --url $API_URL --malformed-every 2 --repeat 3 --delay 0.1

      Watch the rule go from Normal to Pending to Firing under Alerting → Alert rules, and the message arrive in Discord. A few minutes after the traffic stops, a Resolved message follows. How long did it take from the first bad request to the message? Which settings add up to that delay?

      Solution

      Usually two to four minutes. The delay adds up from the scrape interval (15 s on the VM), the [1m] window of rate() that has to fill with errors, the evaluation interval (1 min), the pending period (1 min) and the notification policy's group wait (30 s by default). Each of them trades speed against false alarms: a shorter pending period pages you for every short blip.

    OpenTelemetry

    Prometheus metrics are one kind of telemetry; logs and traces (the path of one request through several services) are the other two. OpenTelemetry (OTel) is the vendor-neutral standard for producing all three: you instrument your code once with the OTel SDK, and send the data with its protocol, OTLP, to an OpenTelemetry Collector that processes it and forwards it to whatever backend you use. Prometheus itself can take metrics pushed over OTLP through its OTLP receiver, which is the push answer to the autoscaling problem above. We use prometheus_client in this course because pull-based metrics are the simplest to see and reason about, but in a new production system OTel is a good default.

    Apply it to your project

    Do these in project time, not during the module:

    1. Instrument your project's API with a request counter, a latency histogram with buckets that fit your latencies, and an error counter by reason.
    2. Run Prometheus and Grafana for your project on an always-on VM that you sized from measurements, reached through an SSH tunnel, with the dashboard and data source provisioned from files in your repository.
    3. Add a Grafana alert on a service metric that notifies a channel your group reads.

    # The API: allow it to scale to zero (it then costs nothing while idle) ...
gcloud run services update classifier-api --region=$REGION --min-instances=0
